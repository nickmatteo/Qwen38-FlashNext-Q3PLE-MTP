## Post 3: Reddit or LocalLLaMA

Title:

Qwen3.8-Flash-Next at 31.45 tok/s on RTX 5070 12GB plus 64GB RAM, with Q3_PLE and learned MTP

Body:

I have been working on a hardware-specific llama.cpp setup for Qwen3.8-Flash-Next on a Windows machine with an RTX 5070 12GB, a Ryzen 5900XT, 64GB DDR4-3000, and one NVMe SSD.

The current target is a 78,525,318,176-byte AtomicChat derivative. I kept the 4.27-bpw neural quant and replaced only `per_layer_token_embd.weight`, the huge n-gram lookup table, with our 3.5-bpw Q3_PLE format. The other 1,223 tensor payloads, totaling 56.1GB, were verified byte-identical to the source.

The draft is Qwen's learned MTP head in a detached 2.20GB sidecar. The winning version fixes the FC/HC tensor layout, quantizes the down experts and output path selectively, keeps gate/up experts at Q4_K, and places routed draft experts in pinned host memory.

The best repeated 16K allocation result was:

| Run | Warm decode | Warm prefill | MTP accepted | Min free VRAM |
| --- | ---: | ---: | ---: | ---: |
| 1 | 31.5021 tok/s | 92.8814 tok/s | 129/129 | 780 MiB |
| 2 | 31.3968 tok/s | 92.8484 tok/s | 129/129 | 776 MiB |
| Mean | 31.4495 tok/s | 92.8649 tok/s | 100% | tight |

Both runs used a 232-token prompt, generated 171 tokens, and matched the expected text and token hashes exactly.

We also tested larger allocations with the same short prompt:

| Allocation | Placement | Warm decode |
| ---: | ---: | ---: |
| 64K | n47 | 26.45 tok/s |
| 80K | n47 | 25.81 tok/s |
| 128K | n47 | 27.41 tok/s |
| 192K | n48 | 26.65 tok/s |
| 224K | n48 | 26.89 tok/s |

Those are capacity tests. They are not 64K to 224K filled-prompt benchmarks.

We tried the filled test next. An 81,920-token allocation with 59,996 content tokens crossed our 6 GiB available-RAM floor and the server reset before a valid completion. A safer n48 path projected roughly 28-33 minutes to rebuild 60K from zero. That is not usable in an agent harness.

The operational design is persisted incremental state. Growing from zero through 16K measured about 42-44 tok/s median/warm. Restoring that state and extending it to exactly 32,768 tokens gave a 36.67 tok/s median for full 512-token additions; resuming the saved 32K pair and chaining it to 49,152 tokens measured 34.08 tok/s median, or 15.06 seconds per addition. The final 48K-to-60K chain appended only 10,848 unseen tokens in 358.08 seconds; warm 512-token additions measured 34.78 tok/s / 14.77 seconds median. The 60K target plus MTP state saved/restored in 1.45/1.16 seconds and reproduced the exact retrieval output with 9/9 drafts after a fresh restart. Its first post-load addition was much colder at 52.10 seconds before warm turns recovered. Minimum free RAM was 6.90 GiB, minimum free VRAM was 2,250 MiB, and pagefile growth was zero. These rows are low-level literal-token continuations, not canonical retokenized chat prompts or filled-context benchmarks; the two-file format also remains experimental and not crash-atomic.

MTP also needs a qualified result. On the exact promoted artifacts and 80K daily profile, rejection-bearing code measured 22.0386 tok/s target-only versus 24.0769 tok/s with MTP, with 210 of 224 drafts accepted. Prose measured 21.8279 versus 19.7634 tok/s, with 130 of 146 accepted. MTP did not match target-only and was not repeat-stable on either fixture, so neither row is a promotable speed result.

The public package will include the exact runtime commit, executable hash, target manifest, sidecar hash, configs, raw JSON, negative tests, and the benchmark contract we are using for occupied context and capability evaluation.

I would especially like reproduction attempts from other 12GB NVIDIA systems and from people working on Qwen4Exp MTP verifier numerics.

## Post 4: LinkedIn

We got Qwen3.8-Flash-Next to 31.45 tokens per second on a single RTX 5070 with 12GB VRAM.

The target model is 78.5GB. The machine has 64GB of DDR4 and one NVMe SSD. There is no second GPU or remote worker in the result.

The main change was separating the model into the parts the hardware actually treats differently.

The neural quant came from AtomicChat's 4.27-bpw build. We replaced only the 51.2B-parameter n-gram lookup table with our Q3_PLE format. We then converted the model's learned MTP head into a detached sidecar and tested several quantization and memory-placement layouts.

The best 16K profile produced two warm runs at 31.50 and 31.40 tokens per second. Both returned the same 171 tokens with exact text and token hashes.

The less flattering results matter just as much.

Our 80K through 224K measurements used a 232-token prompt, so they prove allocation capacity, not filled-context speed. A cold 60K-token fill crossed a 6 GiB available-RAM floor; a safer version projected 28-33 minutes. We rejected full replay and validated persisted incremental agent state instead. Saved state chained from 16K to 32K, 48K, and finally 60K without replay, with 36.67, 34.08, and 34.78 tok/s median 512-token additions (the 60K figure excludes the first cold-residency turn). The 60K state saved/restored in 1.45/1.16 seconds and retained exact 9/9 MTP retrieval behavior after a fresh restart.

MTP also remains experimental. On the 80K daily profile, it was about 9% faster on one warm code pair and about 9% slower on prose. Both rejection-bearing outputs differed from target-only and from the second MTP repeat. We count those as exactness failures, not speedups.

We are turning the work into a reproducible research package with exact source pins, model hashes, raw runs, failed runs, and a broader capability suite. The aim is to give other local-inference builders enough detail to reproduce it or prove it wrong.

## Reddit opening

I have been trying to find the practical boundary for Qwen3.8-Flash-Next Q3_PLE on a consumer Windows system with an RTX 5070 12GB and 64GB DDR4.

The controlled throughput headline is still 31.45 tok/s sustained decode, averaged across two clean 16K-allocation runs. That result used a 232-token prompt and a 171-token completion. It is not a 60K occupied-context result.

The new result is different. I built one canonical chat transcript to a complete assistant-message boundary at 59,750 occupied tokens. The harness saved target and MTP state around 16K, 32K, 47K, and 59.75K. Every later stage started a fresh process, restored the preceding pair, and processed only the unseen suffix.

The actual-depth retrieval test passed exact target/MTP text and token parity across three repeats. Warm decode was 18.25 tok/s target-only and 18.34 tok/s with MTP. MTP drafted 11 tokens and accepted 10, so this was not an all-accepted compatibility trick.

The code result is the useful warning. MTP reached a warm mean of 22.30 tok/s versus 18.15 target-only, and both outputs were semantically valid. But the exact text and retokenized token vectors differed, so I am not presenting that as a speedup. Learned MTP is still workload-dependent on this quantized verifier path.

The broad prose gate also failed target-only instruction following: the model returned a stable 90-word answer to a 170 to 210-word request. That stays in the evidence instead of being tuned away.

The next benchmark layer will put the frozen model behind a lightweight Pi agent and use mini-swe-agent plus the official SWE-bench evaluator for a small pinned coding pilot. The custom harness remains responsible for cache accounting, paired-state integrity, and resource safety.
